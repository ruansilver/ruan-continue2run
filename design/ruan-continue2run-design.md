# ruan-continue2run Skill 设计说明

## 0. 本文档的用途

本文档是提交给 **Skill Creator** 用来生成实际 Skill 文件（`SKILL.md` 及配套 `scripts/`、`references/`）的设计输入。已确定的是**流程编排、Payload 约束、Adapter 契约、日志规则与设计边界**；无法由本文档替用户决定的部分（主要是各 Harness 具体的会话创建调用方式），集中列在第 10 节，需要在 Skill Creator 的访谈/探测阶段（即"Skill 修复阶段"）现场补全。

## 1. 一句话定义

`ruan-continue2run` 被显式触发后，在当前会话结束前，按本会话开场捕获的运行参数，通过对应 Harness 的 Adapter 创建一个新会话，并让新会话携带同一任务入口与本 Skill 自身继续运行，形成接力。Skill 本身只负责**会话接力编排与记录**，保持轻量。

## 2. 设计边界（先说清楚不做什么）

以下内容明确**不在**本 Skill 范围内，Skill Creator 生成时不要加回来：

- 不做任务状态管理（不维护进度、链状态、轮次计数）
- 不做自动完成判断（不判断"任务是否已全部完成"来决定是否继续接力）
- 不做自检机制（不检测创建是否真正成功、不检测是否需要新增 Harness 适配，也不做定期巡检）
- 不判断新会话是否真正运行成功
- 不复制、不注入历史上下文

出问题由用户自行发现（看日志、发现链条中断），需要新增或修复某个 Harness 支持时，由用户显式进入"Skill 修复阶段"。

## 3. 触发条件（用于 SKILL.md 的 description）

- **必须显式调用**，不能通过关键词联想触发。
- 典型使用方式：用户发送"任务入口 + 显式调用本 Skill"。具体触发短语见第 10 节待定项。
- 触发后，本 Skill 只接管"当前会话收尾时的交接动作"，不介入、不评判会话正文任务本身执行得好不好。
- description 措辞宜保守：误触发的代价（不受控地进入放养模式）高于漏触发，与 skill-creator 一般建议的"pushy description"方向相反，需要明确写出"仅在显式调用时使用"。

## 4. 整体流程

```
会话开场   ① 捕获：读取第一条用户消息，构建 RelayContext
   │
会话正文   ② 按放养模式执行任务（黑盒，本 Skill 不关心执行质量）
   │
会话收尾   ③ 写意图日志
   │       ④ 调用 Adapter 创建下一会话（当前会话最后一个有副作用的动作）
   │       ⑤ Adapter 返回后，仅追加一条"创建调用结果"到本会话自己的日志，然后结束
```

第 ⑤ 步说明：创建调用返回后，只允许往**本会话自己的日志文件**追加结果记录，不再执行其他任何动作。因为每个会话写独立日志文件，新旧会话交接重叠时不会互相写同一个文件。

## 5. Relay Payload 与 RelayContext

**Relay Payload 只有三部分，不多不少：**

1. 用户显式任务入口（第一条消息中，剥离触发标记与 Harness 标签后的净化内容）
2. `ruan-continue2run` Skill 自身（新会话开场同样显式调用本 Skill）
3. 当前运行参数：模型标识、思维深度、工作目录，**以及 Harness 标识**

**明确不传：** 历史对话上下文、链状态、轮次信息、任何上一轮的中间结果。

**只认第一条消息：** 会话中途或收尾时用户发的任何消息，一律不进入 Payload，视为噪声。

**历史决策的获取方式：** 不注入，只在放养外壳里给读取指引——做重大决策前，先到日志目录查看同一 slug 下最近的日志。这是指针而不是拷贝，不增加任何状态。真正长期有效的决策，应由任务本身落到需求文档中，日志只负责追溯。

**RelayContext** 是上述 Payload 在运行时的结构化形式，同时也是 Adapter 的输入（见第 7 节）。

## 6. 三段职责

### 6.1 捕获（Capture）

- 时机：会话开场，读取第一条用户消息。
- 动作：识别并剥离触发标记和 Harness 标签，提取运行参数，构建 RelayContext。
- Harness 标签约定：在消息末尾追加 `//HarnessName`。无显式标签时退化为被动探测（探测方式属于各 Harness 适配层的实现细节）。

### 6.2 放养覆盖（Override）

每轮由 Skill 固定叠加的一段文本，不来自捕获：

- 声明本轮为自动接力 / 放养模式。
- 遇到原本要停下来问用户需求的节点：从需求文档与相关参考文档中推断用户意图，结合当前开发阶段（做加法 / 工程收口 / 最终减法）的取向，选择最长远、最有价值的方向实现。
- 无论能否有把握地推断，都不得中断。该约束只针对"任务方向判断"层面，不代表基础设施故障也不会使链条中断。
- 做重大决策前，先读日志目录中同一 slug 下最近的日志，避免与前几轮决策自相矛盾。
- 每次做出关键决策，写入本会话日志。

### 6.3 创建（Create）

创建动作**不在 SKILL.md 内实现**，全部委托给 Adapter（见第 7 节）。SKILL.md 只描述"何时调用 Adapter、传什么、拿到什么后如何记录"。

## 7. Harness Adapter

Skill 本身不绑定任何 Harness 的创建细节，由 Adapter 负责具体实现。

**统一契约：**

| | 内容 |
|---|---|
| 输入 | `RelayContext`：任务入口、Skill（`ruan-continue2run`）、运行参数（模型、思维深度、工作目录）、Harness 信息 |
| 输出 | 创建调用结果：是否已发出、返回信息或错误 |

输出只描述"创建调用本身的结果"，不包含"新会话是否真正运行成功"。

**扩展方式：**

- 新增某个 Harness 支持：新增一个对应的 Adapter，SKILL.md 与日志格式不动。
- 某个 Harness 更新后创建失效：只修该 Harness 对应的 Adapter。
- 以上均通过用户显式进入"Skill 修复阶段"，由 Skill Creator 探测并生成/修改 Adapter，不触碰其他部分。
- 已有的成熟方案（如 Claude Code 的生命周期钩子与会话恢复能力）可直接作为对应 Adapter 的实现起点，不必从零造轮子。

## 8. 日志

- **位置：** 项目级、点前缀目录（具体目录名见第 10 节待定项）。
- **粒度：** 每个会话生成一个独立的时间戳 Markdown 日志文件，不共享、不追加他人的文件。
- **归类：** 由任务入口确定性推导出一个 slug，用 slug 把同一任务的多个会话日志归到一起（体现在文件名或文件头部）。归类靠 slug，不靠共享文件或传递路径，因此 Payload 不需要携带任何日志信息。
- **只记事实：**
  - 意图日志：即将创建下一会话（写于调用 Adapter 之前）
  - 创建调用结果：是否发出、Adapter 返回信息或错误（写于 Adapter 返回之后）
  - 关键决策：遇到的节点、选择的方向、依据的参考文档、把握程度
- **不做的事：** 不判断新会话是否真正运行成功（日志里写"创建调用已发出"，不写"接力完成"）；不承担状态管理。
- 与 Agent Checkpoint / 会话恢复机制保持独立，不合并存储格式。

## 9. 链条终止

没有内部终止条件，也不做完成判断，完全由人类行为自然划界：

- 新会话开场时，检查第一条消息是否符合合法接力载荷格式（有显式调用本 Skill 的标记）。
- 符合 → 按放养模式继续。
- 不符合（例如用户中断后随意发了"继续"或其他内容）→ 按普通会话处理，不套用放养覆盖，链条到此结束。

## 10. 待补全信息（需在 Skill Creator 阶段现场确认）
